PM: Flat reranker, slower vector search. Did the collection size change at all in the last day?
Engineer: It nearly doubled. The nightly ingestion backfilled a large batch of archived projects, so Qdrant is now searching a much bigger index with exactly the same ef parameter as before.
PM: So it is a tuning problem, not a bug in our code. What are the options on the table right now?
Engineer: Three that I can see. We raise the ef search parameter to keep recall and simply eat the latency, we shard the collection by scope so a project query only touches its own shard, or we add a scope pre-filter so the search space shrinks before the vector comparison even runs.
PM: The pre-filter sounds cheapest to try first. Does the payload already carry the scope field we would filter on?
Engineer: It does. Every point has a scope field in its payload, so a filtered search is a one line change on the query side and needs no reindexing of the existing collection at all.
PM: Then let us try the pre-filter today, measure the p95 again against the same query set, and only reach for sharding if the filter alone does not bring us back under the target.
Engineer: Agreed. I will also add an ingestion lag alert so a doubling like this pages us before a user ever notices the regression in their own search results.
PM: Good thinking. While you are in there, can you confirm the filter is applied before scoring and not after, because a post-filter would shrink the result set without saving any of the search cost we care about.
Engineer: Confirmed from the client docs, the filter is a pre-filter that prunes the candidate set during traversal, so it saves the work rather than just trimming the output at the very end.
